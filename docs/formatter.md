# Formatter и линтинг

Команды для проверки и форматирования кода (ESLint, Prettier) и настройка Husky для автоматических
проверок при коммите.

## Команды в package.json

### `npm run lint`

Запускает **ESLint** по всему проекту (`eslint . --max-warnings 0`):

- Проверяет код на соответствие правилам линтинга
- Находит потенциальные ошибки и нарушения code style
- **Не изменяет** файлы, только сообщает об ошибках и предупреждениях
- Завершается с ошибкой (код выхода не 0) при любом **error** или **warning** — коммит и CI не
  пройдут

Используйте перед пушем или в CI для проверки всего кода.

---

### `npm run lint:fix`

Запускает ESLint с автоисправлением (`eslint . --fix --max-warnings 0`):

- Всё то же, что и `lint`
- **Автоматически исправляет** то, что ESLint умеет править (кавычки, точки с запятой, отступы и
  т.п.)
- Остальные проблемы нужно править вручную
- При любом оставшемся warning или error команда завершается с ошибкой

Удобно для быстрого приведения кода в порядок по правилам ESLint.

---

### `npm run prettier`

Проверка форматирования **без изменений** (`prettier --check`):

- Проверяет файлы в `src/**/*.{ts,tsx,css,json}` на соответствие правилам Prettier
- Если форматирование не совпадает — завершается с ошибкой (код выхода не 0)
- **Не записывает** изменения в файлы

Используется в CI и в команде `check`, чтобы пайплайн падал при некорректном форматировании.

---

### `npm run prettier:fix`

Форматирование кода с записью в файлы (`prettier --write`):

- Применяет правила Prettier к `src/**/*.{ts,tsx,css,json}`
- **Перезаписывает** файлы отформатированным кодом

Запускайте вручную, когда нужно выровнять стиль по всему проекту или по изменённым файлам.

---

### `npm run check`

Одна команда для полной проверки перед пушем или в CI:

```bash
npm run lint && npm run prettier
```

- Сначала запускается **lint** (ESLint), затем **prettier** (только проверка)
- Если lint прошёл — запускается **prettier** (только проверка)
- Если любая из команд падает — вся команда завершается с ошибкой

Используйте локально перед `git push` или настройте CI на запуск `npm run check`.

---

### `npm run prepare`

Служебный скрипт для **Husky** (`husky`):

- Вызывается автоматически после `npm install` (в т.ч. в CI и у новых разработчиков)
- Инициализирует Git-хуки в папке `.husky/`
- Вручную вызывать не нужно

---

## Husky: когда и что он делает

**Husky** подключает к репозиторию Git-хуки: скрипты, которые запускаются в определённые моменты
(например, перед коммитом).

### Как настроен проект

- В `package.json` в скрипте `prepare` указано: `"prepare": "husky"` — при установке зависимостей
  Husky настраивает папку `.husky/` как каталог с хуками (`core.hooksPath`).
- В `.husky/pre-commit` записана одна команда: **`npx lint-staged`**.

То есть при каждом коммите Git запускает `.husky/pre-commit`, а тот — **lint-staged**.

### Что такое lint-staged

**lint-staged** запускает заданные команды только для файлов, попавших в индекс Git (staged), т.е.
для тех, что вы добавили в коммит через `git add`.

В `package.json` секция `lint-staged` настроена так:

| Файлы                 | Команды                                  |
|-----------------------|------------------------------------------|
| `src/**/*.{ts,tsx}`   | `eslint --fix`, затем `prettier --write` |
| `src/**/*.{css,json}` | `prettier --write`                       |

То есть при коммите:

1. По **staged** `.ts` и `.tsx` запускаются ESLint с автофиксом и Prettier (с записью).
2. По **staged** `.css` и `.json` запускается только Prettier (с записью).

Если **ESLint** завершится с ненулевым кодом (ошибка или предупреждение, используется
`--max-warnings 0`) — скрипт pre-commit падает и **коммит не создаётся**. Исправления нужно внести в
код и снова добавить файлы в индекс.

### Когда срабатывает

| Событие                           | Действие                                                                                                                            |
|-----------------------------------|-------------------------------------------------------------------------------------------------------------------------------------|
| `git commit`                      | Выполняется `.husky/pre-commit` → `npx lint-staged` по staged-файлам. При любой ошибке или предупреждении ESLint коммит отменяется. |
| `npm install`                     | Выполняется `prepare` → `husky` — хуки устанавливаются/обновляются.                                                                 |
| Клонирование репо + `npm install` | Хуки ставятся автоматически, дальше при коммитах всё работает как выше.                                                             |

### Обход хука (не рекомендуется)

Коммит без проверок:

```bash
git commit --no-verify -m "message"
```

Использовать только в исключительных случаях; в ветке `master` дополнительную проверку даёт CI (
lint + prettier check).

### Итог

- **При коммите** Husky запускает lint-staged → по staged-файлам выполняются ESLint (с fix и
  `--max-warnings 0`) и Prettier (с write). Коммит блокируется при любых ошибках или предупреждениях
  ESLint.
- **В CI** (например, на push в `master`) имеет смысл запускать `npm run check` (lint + prettier
  check), чтобы отклонять код с ошибками/предупреждениями линтера или неверным форматированием даже
  при коммите с `--no-verify`.

Подробнее про структуру хуков: папка [.husky](../.husky) в корне проекта.
